# Smart Schedule Coordinator

**大学のダンス練習で生まれた、開催場所と複数回の開催を考慮する日程調整Webアプリです。**

[公開アプリを開く](https://shin-systems26.github.io/schedule-app/) · [ソースコード](https://github.com/shin-systems26/schedule-app) · [変更履歴・プルリクエスト](https://github.com/shin-systems26/schedule-app/pulls?q=is%3Apr+is%3Amerged)

参加者が○・×・？で予定を回答し、主催者が集計結果を確認します。全員が同時に集まる候補に加え、最大2回の対面練習を組み合わせ、登録された回答者全員に少なくとも1回の参加機会を確保する案を探せます。

個人開発として、実際の練習日程の調整に使いながら改善しています。実装・テストには生成AIの支援を利用しています。以下では、開発者自身が行った課題発見・要件決定と、AIによる実装支援を区別して記載しています。

## 開発の背景

大学のダンス練習では、授業やキャンパスの違いから全員の予定が一致しにくく、集まれる時間が夜遅くなるという課題がありました。また、対面で参加できる時間とオンラインで参加できる時間は同じではありません。

そこで「全員が同じ日に集まる」だけでなく、「2回に分ければ全員に参加機会を作れるか」を考えるようにしました。例えば、1回目に2人、2回目に3人が参加できれば、5人全員が少なくとも1回参加できます。同じ人が両方に参加できる場合も、全体の参加人数では重複して数えません。

主催者として重視したのは、できるだけ対面で練習し、平日19時頃までに開始することです。対面で全員の参加機会を確保できない場合には、オンライン1回の候補も比較できるようにしました。

## 実際に使いながら改善した経過

### 1. 管理画面への入口が分かりにくかった

ログイン・イベント作成・イベント管理が別々のURLに分かれていました。利用時にリンクを使い分ける負担を感じ、管理者ホームへの統合を要件にしました。

現在はトップページでGoogleログイン、作成、自分のイベント一覧、回答確認、受付管理まで行えます。参加者には専用の回答リンクを共有します。旧HTMLへのリンクは転送し、既存の回答形式も読み取る構成にしました。

### 2. 日時を細かく入力するほど、回答が面倒になった

授業時間に合わせた入力や細かい時間刻みを試しましたが、操作が複雑になり、使いにくさを感じました。そのため、機能を増やすだけでなく入力方法を見直しました。

現在は平日の「朝・1〜5限・放課後」、土日の「午前・午後・夜」で普段の予定を入力し、特定の日だけ30分単位で修正します。さらに、どの質問からでも別の質問へ回答をコピーできるようにしました。コピー後はそれぞれ独立して編集でき、直前の操作は取り消せます。

### 3. 全員が同時に集まる候補だけでは調整が進まなかった

全員の予定が一致しない場合にも練習を実施できるよう、複数回の組み合わせを求める機能を追加しました。当初の通常・分割というモード分けや独立した分割調整欄は、利用時の要望に合わせて整理しました。

現在は通常ランキングを残し、その下に「おすすめ練習日程をまとめて探す」を配置しています。対面は最大2回・各回最低2人・1時間とし、キャンパスをまたぐ組み合わせも比較します。同じ日の2回開催も、前の回の終了から次の回の開始まで2時間以上空けば候補にします。

### 4. 実際の開催には、場所ごとの条件が必要だった

工学キャンパスでは指定した人が必ず参加する必要がある、主催者自身が参加できない日を外したい、という運用上の条件を追加しました。その後、環境人間キャンパスにも独立した必須メンバー指定を追加しています。

各キャンパスの必須メンバーは、その場所で開催する各回の全時間帯で○が必要です。対面とオンラインの除外日も別々に設定でき、条件変更後に再検索できます。

### 5. ランキングとおすすめの違いに気づいた

実際に使って「ランキングには×のある候補が出るのに、おすすめには○と？だけの候補が出る」と疑問を持ち、同じイベントの日時と回答内訳の照合を依頼しました。

確認した候補では回答の判定は一致していましたが、○の人数を優先する順位付けと、上位10件の表示制限によって、全員が参加できる可能性のある候補が埋もれていました。そこで順位を「全員○ → ○と？だけで全員を含む → その他」に変更し、全期間の候補を20件ずつ最後まで確認できるようにしました。

また、？を含む案は参加確定ではないため、○だけで参加機会を確保できる人数と、確認が必要な人を分けて表示しています。

### 6. 「検索しても反応しない」を再現して確認した

除外日に11月4日を入力した際、検索ボタンを押しても反応しないという問題がありました。調査では、イベント期間外の日付が入力欄に残ると、ブラウザー標準の検証が送信を止め、アプリの説明が表示されないケースを確認しました。

アプリ側で入力日付を検証し、指定できる期間とエラー理由を表示するよう修正しました。期間内・期間外、直接入力して検索、重複追加、全日除外、解除、エラーからの復帰をテストしました。

これらの改善は「実際に操作する → 違和感や不足を伝える → 条件を具体化する → AIの支援で実装・検証する」という流れで進めています。入力時間の短縮率や満足度などの効果測定は未実施で、数値的な成果としては主張していません。

## 開発者の役割とAIの活用

**開発者自身が行ったこと**

- 実際のダンス練習で、予定が合わない・入力が面倒・候補が分かりにくいという課題を発見した。
- 対面優先、最大2回、開始時間、キャンパス別の必須メンバー、除外日などの要件を決めた。
- 画面を使って、複雑になった入力方法の見直しや、検索結果の検証を依頼した。
- 改善の優先順位を決め、実際の用途に合うかを確認した。

**AIの支援を受けたこと**

ChatGPT・Codexを利用し、設計案の検討、コード生成、修正、テストコード作成・実行、GitHubへの反映、ドキュメント整理を進めました。実装と自動テストの多くはAIの支援によるもので、すべてを独力で実装した作品ではありません。

開発を通じて、必要な条件を具体的に伝えること、出力を実際の回答と照らすこと、検証済みの範囲と未確認の範囲を分けることの重要性を学んでいます。生成されたコードの理解を深めることも継続課題です。

## 現在の使い方

### 管理者

1. [管理者ホーム](https://shin-systems26.github.io/schedule-app/)でGoogleログインする。
2. イベント名と期間を入力して作成する。新規イベントの質問は、オンライン・環境人間キャンパス・工学キャンパスの固定3項目。
3. 参加者用リンクをコピーして共有する。
4. 「回答を更新」で最新の回答を取得する。回答一覧は質問・日付・個人別に確認できる。
5. 通常ランキングを30分／1時間で切り替える。11位以降も「次の20件を表示」で確認できる。
6. おすすめ検索では工学の必須メンバーを指定し、必要に応じて環境人間の必須メンバー、対面／オンラインそれぞれの除外日を設定して検索する。
7. 未確定の人を含む案も検討する場合は「？も含めた確認用の案を探す」を選ぶ。対象者に確認してから開催を決める。

受付の締切・再開と、イベント・回答の削除も管理者ホームから操作できます。削除は取り消せません。

### 参加者

共有された `respond.html?event=イベントID` を開き、名前と予定を入力して送信します。参加者のログインは不要です。

平日は朝・1〜5限・放課後、土日は午前・午後・夜で入力します。授業時間と重なる30分枠に反映し、例えば1限は9:00〜10:30、2限は10:30〜12:30です。重なる区分は入力済みの×・？・○の順に優先します。

「特定の日だけ細かく修正する」では8:00〜22:00を30分単位で修正できます。特定日の修正は曜日設定より優先されます。質問間のコピーは曜日設定と特定日の修正の両方を含みます。細かな日時表は横スクロールに対応しています。

## 集計とおすすめ検索の条件

### 通常ランキング

全員○、○と？だけで全員を含む候補、その他の順に並べます。各区分内では○の多さ、×の少なさ、未回答の少なさ、参考スコア、日時順で比較します。参考スコアは `○×3 + ？×0.5 − ××4` です。

開催時間全体の回答を確認し、一部だけ○の人を1時間参加可能とは数えません。保存されていない回答は？と区別し、全員に保存データがない時間帯は表示しません。新しい入力フォームでは初期値の？も送信時に保存されます。

通常ランキングには、おすすめ検索の除外日・必須メンバー条件は適用しません。

### おすすめ練習日程

- **対面：** 平日8:00〜19:00開始、1回1時間、各回最低2人、最大2回。両キャンパスの組み合わせも比較する。同日2回は終了から次の開始まで2時間以上空ける。
- **オンライン：** 土日も含め8:00〜21:00開始、22:00までに終了する1時間で、登録回答者全員を含む候補を探す。
- **必須メンバー：** 工学は1人以上指定。環境人間は未指定なら制約なし。指定した全員が、そのキャンパスの各回で○であることが必要。オンラインには適用しない。
- **除外日：** 対面とオンラインで独立して複数追加・解除できる。イベント期間内のみ指定できる。
- **？を含む検索：** 明示的な？を確認待ちとして含める。×・保存のない回答は含めず、必須メンバーの○条件も緩めない。

参加機会を確保できる人数、○のみで確保できる人数、開催回数の少なさ、各プランで最も遅い開始時刻の早さ、人数差の小ささを順に比較し、対面・オンラインそれぞれ最大3案を表示します。対面で全員を含めない場合も、未カバー者を示した代替案を表示します。

計算はブラウザーのWeb Worker内で実行します。対面の2回の組み合わせは最大50万組まで比較し、上限に達した場合は暫定案と表示します。実行時間の上限は20秒です。探索上限に達した結果から「100％にできる案は存在しない」とは断定できません。

## 現在の制約

- おすすめ検索は1時間・上位3案。30分候補は通常ランキングで確認する。
- 「全員」は登録された回答ドキュメントを対象とする。未回答の人を含む名簿管理や、同一人物の重複送信の自動判別はない。同名でもIDが異なれば別回答として数える。
- 主催者が回答しない運用を想定している。主催者の参加可否は除外日と最終確認で補う。主催者も回答すれば、その回答も人数に含まれる。
- 除外日・必須メンバー・計算結果は画面内だけで有効。再読み込みやイベント移動でリセットされる。
- 参加者による送信済み回答の編集、プラン保存、参加確定、参加者への自動通知は未対応。
- 日程の計算自体は決められた条件による集計・組み合わせ探索であり、生成AIによる予測ではない。

## 技術構成とデータ

HTML・CSS・JavaScriptで画面と集計を実装し、Firebase AuthenticationでGoogleログイン、Cloud Firestoreでイベントと回答を保存しています。GitHub Pagesで公開し、Git／GitHubで変更履歴を管理しています。専用のアプリケーションサーバーは置いていません。

```text
events/{eventId}
  title, startDate, endDate, ownerId, isOpen, groups, createdAt
  responses/{responseId}
    name, answers, createdAt
```

`answers` は質問IDごとに日時区間と `yes` / `no` / `maybe` を保存します。旧 `questions` や旧固定3項目の質問設定、`response[groupId]` 形式の回答、従来の1時間・10分境界の回答も読み取ります。通常は30分刻みで候補を作り、古い10分境界の回答がある場合は10分刻みを維持します。

主なファイルは次のとおりです。

- `index.html` / `dashboard.js` / `dashboard.css`：管理者ホーム、認証、作成、一覧、受付管理
- `respond.html` / `respond.js` / `response-model.js`：参加者画面と曜日・特定日の回答処理
- `firebase.js` / `event.js` / `response.js` / `groups.js`：Firebase接続、取得・保存、新旧質問設定
- `time-data.js` / `ranking.js` / `response-view.js`：日時区間の共通判定、ランキング、回答一覧
- `practice-ui.js` / `practice-planner.js` / `practice-worker.js`：現在のおすすめ検索
- `firestore.rules`：アクセス制御のルール
- `tests/`：計算テストとFirebaseを模擬する画面テスト

`login.html` / `create.html` / `admin.html` は旧URLからの転送用です。`split-*.js` は旧分割機能のコードとして残っていますが、現在の管理画面は `practice-*.js` を利用します。

## アクセス制御と公開

認証はFirebase Authentication、データの読み書き制御はFirestore Security Rulesで行います。画面でボタンを隠すだけの制御ではありません。

イベントの個別情報は参加者向けに公開され、イベント一覧・回答の閲覧は所有者に制限します。受付中のイベントに対する回答作成はログイン不要ですが、回答の更新は禁止しています。回答作成時は名前と回答マップの基本的な形式を検証します。イベント削除は受付を閉じ、回答を400件ずつ削除した後、親イベントを削除します。

実際の参加者名・回答はFirestoreに保存し、リポジトリのテストには架空データを使います。GitHub Pagesへの反映だけではSecurity Rulesは更新されません。RulesはFirebase側で別途反映・検証する必要があります。

公開ドメインを変更した場合は、Firebase Authenticationの承認済みドメインを確認してください。現在の公開先は `shin-systems26.github.io` で、Firebaseの `authDomain` をGitHub Pagesのホスト名に置き換える必要はありません。

## 動作確認

リポジトリのフォルダーで、Node.jsを使って実行します。

```sh
node --test tests/*.test.mjs
node tests/server.cjs
```

サーバー起動後、[ローカル画面テスト](http://127.0.0.1:8765/tests/browser.html)を開きます。Firebaseをメモリ内のデータに置き換えるため、本番のイベントや回答は変更しません。Playwrightと対応ブラウザーが導入済みなら、別のターミナルで `node --test tests/flows.cjs` を実行する方法もあります。

**2026年11月9日の確認結果**

- 計算テスト54件、画面テスト27件が成功。
- 既存テストに加え、参加者2〜10人・両キャンパスの必須条件・除外日・○／×／？／未回答を組み合わせた500ケースを一時検証スクリプトで別計算と照合し、一致を確認。この追加スクリプトはリポジトリ収録テストには含まない。
- 20人・30日分の合成データで466,095組を約0.7秒で比較。開発環境での測定であり、すべての端末での速度保証ではない。
- 本番への未ログイン読取で、イベント一覧403・個別イベント200・回答一覧403を確認。
- 公開中の主要HTML／JavaScript 7ファイルとローカルの一致を確認。

画面テストには、入力・コピー・送信、旧データ互換、30分／1時間ランキング、全候補のページ表示、除外日の追加・解除・入力エラー復帰、キャンパス別必須メンバー、受付締切・再開、削除、ログアウト時の個人情報表示消去を含みます。

この確認結果は、本番Googleログインの再認証や実データの作成・削除の一連の操作、全ブラウザー・実機、Security Rulesの全操作を検証したことを意味しません。テストで確認できた範囲と運用上の確認を分けて管理しています。

## 今後取り組みたいこと

利用者からのフィードバックと入力時間を測定し、改善効果を確かめたいと考えています。また、おすすめ検索の30分対応や条件の分かりやすさ、送信済み回答の編集・重複回答への対応を検討しています。コードの理解を深め、本番認証と権限を含む検証範囲を広げることも課題です。
